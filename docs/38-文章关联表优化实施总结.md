# 文章关联表优化实施总结

## 实施时间
2026年1月2日

## 背景
发现Neon数据库计算时间过高（10.26小时），分析后发现文章详情页查询相关文章时使用了低效的查询方式（每次查询100条文章），导致数据库负载过高。

## 实施方案
创建文章关联表（ArticleRelation），预计算并存储文章间的关联关系，将O(n)的查询优化为O(1)。

## 已完成的工作

### 1. 数据库Schema更新
**文件**: `prisma/schema.prisma`

添加了ArticleRelation模型和相关枚举：
```prisma
model ArticleRelation {
  id                Int      @id @default(autoincrement())
  articleId         Int
  article           Article   @relation("SourceArticle", fields: [articleId], references: [id], onDelete: Cascade)
  relatedArticleId  Int
  relatedArticle    Article   @relation("RelatedArticle", fields: [relatedArticleId], references: [id], onDelete: Cascade)
  type              RelationType
  weight            Int       @default(0)
  matchedTags       String?   @db.Text
  createdAt         DateTime  @default(now())
  updatedAt         DateTime  @updatedAt
  
  @@unique([articleId, relatedArticleId, type])
  @@index([articleId])
  @@index([relatedArticleId])
  @@index([type])
  @@index([weight])
  @@map("article_relations")
}

enum RelationType {
  CATEGORY
  TAG
}
```

### 2. 关联生成脚本
**文件**: `scripts/generate-article-relations.ts`

功能：
- 为单篇文章生成6篇相关文章
- 策略：优先同分类（权重100），不足则补充同标签（权重=匹配标签数*10）
- 按需生成：第一次访问时创建
- 自动补充：如果不足6篇，下次访问时补充

使用方法：
```bash
# 为指定文章生成关联
npx tsx scripts/generate-article-relations.ts <articleId>

# 为所有文章生成关联
npx tsx scripts/generate-article-relations.ts all
```

### 3. 查询函数优化
**文件**: `lib/blog.ts`

新增函数：
- `getRelatedPosts(articleId, limit=6)`: 获取相关文章
  - 先查询已有关联
  - 如果不足6篇，异步生成新关联
  - 返回现有关联（即使不足）
- `generateRelationsAsync(articleId)`: 异步生成关联关系

### 4. 文章详情页更新
**文件**: `app/blog/[slug]/page.tsx`

优化前：
```typescript
const posts = await getAllPosts()
const relatedPosts = posts
  .filter(post => post.id !== post.id && post.categoryId === post.categoryId)
  .slice(0, 6)
```

优化后：
```typescript
const relatedPosts = await getRelatedPosts(post.id, 6)
```

### 5. 删除文章时清理关联记录
**文件**: `app/api/articles/[slug]/route.ts`

在DELETE方法中添加：
```typescript
// 删除文章的所有关联记录（该文章作为源文章的关联）
await prisma.articleRelation.deleteMany({
  where: { articleId },
})

// 删除其他文章指向该文章的关联记录（该文章作为被关联文章的记录）
await prisma.articleRelation.deleteMany({
  where: { relatedArticleId: articleId },
})
```

## 性能对比

### 优化前
- **查询方式**: 每次加载文章详情页查询所有文章（100+条）
- **时间复杂度**: O(n)
- **数据库负载**: 高
- **响应时间**: ~500ms
- **Neon计算时间**: 10.26小时/月

### 优化后
- **查询方式**: 直接查询预计算的关联表
- **时间复杂度**: O(1)
- **数据库负载**: 低
- **响应时间**: ~50ms（预计提升10倍）
- **Neon计算时间**: 预计降至1小时/月

## 创建策略

采用**方案3：按需生成**（用户选择）

### 优势
1. **资源高效**: 只为实际被访问的文章生成关联
2. **用户优先**: 测试人员先访问生成关联，用户访问时直接使用
3. **自动补充**: 如果关联不足，下次访问时自动补充
4. **后台处理**: 异步生成不阻塞用户请求

### 工作流程
1. 用户访问文章详情页
2. 系统查询关联表
3. 如果有足够关联（≥6篇），直接返回
4. 如果不足，在后台异步生成新关联
5. 返回现有关联（即使不足）
6. 下次用户访问时使用完整关联

## 索引优化

为article_relations表创建了4个索引：
1. `articleId`: 加速查询某文章的所有关联
2. `relatedArticleId`: 加速反向查询
3. `type`: 支持按类型筛选
4. `weight`: 支持按权重排序

## 数据一致性

通过Prisma的`onDelete: Cascade`确保：
- 删除文章时，自动删除关联记录
- 防止孤立关联记录

额外在删除API中显式清理：
- 删除该文章作为源文章的关联
- 删除其他文章指向该文章的关联

2. **关联查询性能**: 监控`getRelatedPosts`响应时间

## 后续优化方向

1. **批量预生成**: 在低峰期为所有文章预生成关联
2. **关联更新策略**: 文章内容/标签变化时是否更新关联
3. **关联算法优化**: 引入更多相关性因素（如关键词、阅读时长）
4. **缓存策略**: 对热点文章的关联结果进行缓存
5. **A/B测试**: 对比不同关联算法的用户点击率
